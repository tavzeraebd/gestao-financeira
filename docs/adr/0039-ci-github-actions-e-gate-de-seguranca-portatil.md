# ADR-0039 — CI no GitHub Actions: qualidade sem Docker por padrão, banco/E2E em workflow separado, gate de segurança portátil

Status: aceita (2026-10-28, Etapa 9) · Escopo: `.github/workflows/ci.yml`, `.github/workflows/ci-docker.yml`, `scripts/security-checks.ts`, script `security:check`, seção "CI" do `README.md` · Complementa ADR-0002, ADR-0032

**Contexto.** O repositório (`origin` em GitHub) não tem CI. As verificações que exigem Docker local (pgTAP, integração, E2E autenticado) estão pendentes desde as Etapas 6 e 7 por falta de Docker Desktop **na máquina de desenvolvimento**; os runners hospedados do GitHub (`ubuntu-latest`) trazem Docker (a confirmar na primeira execução). O security gate oficial (`~/.claude/factory/security/gate.mjs`) é ferramenta pessoal e não existe no runner. A política de dependências exige a versão mais atual e `pnpm audit` limpo, com exceção datada em `.depsignore` (TypeScript 7).

**Decisão.**
1. **`ci.yml`** (em `push` para `main` e `pull_request`), `permissions: contents: read`, `concurrency` com cancelamento, `timeout-minutes` em todo job, Node pelo `.nvmrc`, pnpm pelo `packageManager`, `pnpm install --frozen-lockfile`. Jobs: **quality** (`pnpm lint`, `pnpm typecheck`, `pnpm test`, `pnpm format:check`); **build** (`pnpm build` com `NEXT_PUBLIC_SUPABASE_URL`/`PUBLISHABLE_KEY`/`APP_URL` fictícios, como o `playwright.publico.config.ts`); **e2e-publico** (`playwright install --with-deps chromium`, `pnpm test:e2e:publico`, relatório como artefato em falha); **security** (`pnpm security:check` e `pnpm audit --audit-level=high`); **outdated** (`pnpm outdated`, apenas informativo, `continue-on-error`, porque a exceção do TypeScript 7 vive em `.depsignore`).
2. **`ci-docker.yml`** (`workflow_dispatch` e `pull_request` condicionado a `vars.CI_DOCKER == 'true'`): `supabase/setup-cli`, `supabase start`, `pnpm db:lint`, `pnpm db:test`, `pnpm db:types` com `git diff --exit-code src/types/database.ts`, `pnpm test:integration`, `pnpm test:e2e`. Fica **desligado por padrão** (a primeira execução vai concentrar o atraso acumulado de pgTAP/integração/E2E das Etapas 6–9 e pode vir vermelha); o usuário liga com a variável do repositório ou dispara à mão. Segredos de teste são os do Supabase **local** (`supabase status -o env`), mascarados, nunca segredos de produção.
3. **Gate portátil** `scripts/security-checks.ts` (TypeScript, executado com `node`), sem dependência nova: (a) nenhum arquivo versionado com padrão de segredo (chaves `sb_secret_`, JWT de `service_role`, blocos de chave privada); (b) `SUPABASE_SECRET_KEY` fora de `src/`; (c) nenhum hex de cor fora de `globals.css`, `manifest.ts` e do `viewport`; (d) `unstable_cache`/`use cache` ausentes (ADR-0015); (e) `dangerouslySetInnerHTML` só nos arquivos permitidos; (f) `'unsafe-inline'`/`'unsafe-eval'` ausentes de `script-src` em `src/lib/csp.ts`; (g) workflows: ações fixadas por **SHA de commit completo**, `permissions` declarado, nenhum `pull_request_target`, nenhum `secrets.` em job de PR de fork. Não substitui o gate pessoal, que continua obrigatório antes de relatar sucesso.
4. **Migrations em produção não rodam no CI.** `supabase db push --linked` exige token e senha do banco de produção; fica manual (runbook `docs/runbooks/migracoes-producao.md`), executado pelo usuário ou por agente autorizado, com `--dry-run`, lint remoto e conferência da lista de migrations depois.
5. **Deploy**: o Render continua publicando a partir de `main`; exigir CI verde antes do deploy é configuração do Render/GitHub (proteção de branch, "after CI checks pass"), item do usuário.

**Alternativas.**
- Rodar pgTAP/E2E em todo PR já: bloqueia o fluxo enquanto o atraso acumulado não for quitado; o workflow separado permite quitar uma vez e depois ligar.
- Ferramentas de terceiros (gitleaks, Snyk, CodeQL): dependência/licença/conta; CodeQL é gratuito para repositório público e pode ser ligado nas configurações do GitHub sem código (sugestão ao usuário, não requisito).
- Aplicar migrations a partir do CI: segredo de escrita em produção em runner; rejeitado nesta etapa.
- Copiar o `gate.mjs` pessoal para o repositório: acopla o projeto à fábrica local.

**Consequências.** A primeira execução no GitHub é o teste real dos workflows (não há `act` nem Docker local para ensaiá-los); o QA entrega os arquivos validados por `security:check` e o usuário/agente autorizado faz o push. O custo de minutos do Actions é pequeno e controlado por `concurrency` e `timeout`. `actions/*` e `pnpm/action-setup` ficam fixadas por SHA e atualizadas à mão.
